## 测试类型

**按阶段分**：
- **单元测试**：测试最小可测单元（函数/类），通常由开发人员完成，白盒为主
- **集成测试**：测试模块间接口和交互，发现接口错误
  - 自顶向下：从主模块开始，逐步加入下层模块（需要桩）
  - 自底向上：从底层模块开始，逐步集成（需要驱动）
  - 大爆炸：所有模块一次集成（风险高）
- **系统测试**：在完整系统上进行功能、性能、安全等测试
- **验收测试**：用户验证系统是否满足需求
  - Alpha 测试：用户在开发环境下测试，开发人员在旁
  - Beta 测试：用户在实际环境下测试，开发人员不在场

**按目的分**：性能测试、压力测试、负载测试、安全测试、回归测试、兼容性测试

## 黑盒测试

不关心内部实现，只关注输入输出。

**等价类划分**：
- 将输入域划分为若干等价类（有效/无效）
- 从每个等价类中取一个代表值作为测试用例
- 例：年龄输入框，有效类[1,120]，无效类<0，>120

**边界值分析**：
- 在等价类边界处取值（边界值 ±1）
- 例：[1,120] → 测试 0, 1, 2, 119, 120, 121

**因果图**：
- 分析输入条件（因）和输出结果（果）之间的逻辑关系
- 最终生成判定表

**判定表**：
- 列出所有输入条件组合和对应输出，系统化地设计测试用例

## 白盒测试

关注代码内部逻辑，验证每条路径都被测试到。

**覆盖准则**（从弱到强）：

| 覆盖类型 | 要求 |
|---------|------|
| 语句覆盖 | 每条语句至少执行一次 |
| 判定覆盖（分支覆盖） | 每个判断的 true/false 都覆盖 |
| 条件覆盖 | 每个判断中的每个条件的 true/false 都覆盖 |
| 判定/条件覆盖 | 同时满足判定覆盖和条件覆盖 |
| 条件组合覆盖 | 每个判断中所有条件值的组合都覆盖 |
| 路径覆盖 | 覆盖所有可能路径（最强，组合爆炸） |

**考点**：条件覆盖不一定能满足判定覆盖！

**控制流图与环形复杂度**：
- 环形复杂度 V(G) = 边数 - 节点数 + 2（或判断节点数 + 1）
- V(G) 表示独立路径数，也是路径覆盖所需的最少测试用例数

## 软件质量模型（ISO/IEC 9126）

六大质量特性：

| 特性 | 子特性 | 说明 |
|------|--------|------|
| **功能性** | 适合性、准确性、互操作性、安全性 | 是否实现了所需功能 |
| **可靠性** | 成熟性、容错性、可恢复性 | 在规定条件下维持性能 |
| **易用性** | 可理解性、可学习性、可操作性 | 用户使用的难易程度 |
| **效率** | 时间特性、资源特性 | 性能与资源占用 |
| **可维护性** | 可分析性、可修改性、稳定性、可测试性 | 修改的容易程度 |
| **可移植性** | 适应性、可安装性、共存性、可替换性 | 迁移到其他环境的能力 |

## CMM/CMMI

**CMM 五个级别**：

| 级别 | 名称 | 特征 |
|------|------|------|
| 1 | 初始级 | 过程混乱，依赖个人英雄主义 |
| 2 | 可重复级 | 基本项目管理过程已建立 |
| 3 | 已定义级 | 过程标准化，全组织文档化 |
| 4 | 已管理级 | 定量管理过程和产品质量 |
| 5 | 优化级 | 持续过程改进 |

**CMMI**：CMM 的升级版，融合了软件、系统、集成产品开发
- **阶段式**：1~5级（同CMM）
- **连续式**：按能力域分别评级（0~5）

**考点**：国内软件企业通常目标是通过 CMMI 3 级认证。

## 软件评审

- **技术评审**：检查设计文档、代码
- **代码走查（Code Walkthrough）**：作者逐行解释代码，团队提问
- **代码审查（Code Inspection/Review）**：正式，有检查表，角色分工（主持人、作者、评审员、记录员）
- **正式技术评审（FTR）**：最正式的形式

## 测试驱动开发 TDD

```
红（Red）：先写一个失败的测试
绿（Green）：写最少的代码让测试通过
重构（Refactor）：改善代码，确保测试仍通过
```

- 测试即文档
- 强迫先思考接口设计
- 重构时有安全网

## 常见坑

- Alpha 测试 = 用户在**开发方**环境测试（开发人员**在场**）
- Beta 测试 = 用户在**用户方**环境测试（开发人员**不在场**）
- 条件覆盖 ≠ 判定覆盖，两者不互相包含
- CMM 第1级不叫"无序"，叫"初始级"
