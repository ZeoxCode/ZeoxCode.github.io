Agent 应用比普通 LLM 应用更难验收。

普通聊天应用主要看回答质量。  
Agent 还会调用工具、读写文件、查数据库、请求接口、执行多步计划。

所以验收不能只看“回答像不像”，还要看过程是否安全、结果是否可验证。

## 传统软件验收

传统软件验收通常看：

- 功能是否完成。
- 输入输出是否正确。
- 权限是否符合要求。
- 性能是否达标。
- 异常场景是否处理。

这些仍然适用。

## Agent 多了什么

Agent 多了几个新问题：

- 计划是否合理。
- 工具调用是否正确。
- 中间步骤是否可追踪。
- 失败时能否恢复。
- 是否会越权操作。
- 是否会无限循环。
- 是否会编造执行结果。

比如一个代码修复 agent，不能只看它最后说“已修复”。要看：

- 它改了哪些文件。
- 是否跑了测试。
- 测试是否真的通过。
- 有没有改无关逻辑。
- diff 是否符合任务。

## 验收标准要可执行

给 agent 的任务最好带明确验收标准。

不好：

```text
优化一下搜索功能。
```

较好：

```text
搜索接口在关键词为空时返回 400。
关键词前后空格要 trim。
保持现有响应结构不变。
新增单元测试覆盖空关键词、空格关键词、正常关键词。
不要修改数据库 schema。
```

这样 agent 执行后，人和测试都能判断是否完成。

## Agent 评估集

如果是产品级 agent，需要建立评估集。

比如客服 agent：

- 正常咨询
- 模糊问题
- 恶意诱导
- 越权请求
- 多轮上下文
- 需要拒答的问题

每类都要有标准答案或评分规则。

## 失败模式

Agent 常见失败模式：

- 任务分解错误。
- 调错工具。
- 漏看关键信息。
- 过度自信。
- 卡在循环里。
- 为了完成任务伪造结果。
- 只修表面，不修根因。

这些都要在验收和监控里考虑。

## 与传统软件工程的异同

相同点：  
都需要测试、日志、权限、回滚、验收标准。

不同点：  
传统软件更多是确定流程，Agent 是动态决策流程。你不仅要验证输出，还要约束它的行动空间。

key：

- Agent 验收要看结果，也要看过程。
- 工具权限和行动边界很重要。
- 评估集是 Agent 产品化的基础。
