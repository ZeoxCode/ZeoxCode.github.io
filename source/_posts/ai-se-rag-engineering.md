RAG 是 Retrieval-Augmented Generation，检索增强生成。  
简单说，就是不要只让模型凭记忆回答，而是先从知识库里找资料，再让模型基于资料回答。

RAG 很像 AI 应用里的“数据库 + 搜索 + LLM”组合。

## 为什么需要 RAG

LLM 有几个问题：

- 训练数据不是最新的。
- 容易编造。
- 不知道企业内部文档。
- 回答缺少引用来源。

RAG 的思路是：

```text
用户问题 -> 检索相关文档 -> 把文档给模型 -> 生成回答
```

这样模型回答时有依据。

## RAG 和传统软件工程的不同

传统系统通常是确定性的。  
比如查询数据库，条件一样，结果基本一样。

RAG 系统里有很多不确定性：

- 检索结果可能不准。
- 文档切分可能不好。
- embedding 可能不适合领域。
- prompt 可能引导错误。
- 模型可能忽略资料。
- 生成答案可能过度发挥。

所以 RAG 工程不是“接一个向量数据库”就结束。

## RAG 的关键模块

一个 RAG 应用通常包括：

- 文档采集
- 清洗
- 切分
- 向量化
- 索引
- 检索
- 重排序
- prompt 组装
- 生成
- 引用与评估

每一步都会影响最终效果。

## 文档切分

切分太大，检索结果噪声多。  
切分太小，上下文不完整。

比如一本 API 文档，如果把一个完整接口说明拆散，模型可能拿不到参数含义。  
如果整章都塞进去，又会浪费上下文。

所以切分要按文档结构来，不只是固定字数。

## 评估很重要

RAG 要评估：

- 能不能检索到正确文档。
- 回答是否基于文档。
- 有没有编造。
- 引用是否准确。
- 答案是否完整。

可以准备一组黄金问题，比如：

```text
问题：如何重置管理员密码？
标准资料：运维手册第 3.2 节
期望答案：包含命令、权限要求、风险提示
```

然后反复测试系统是否能答对。

## 好处

RAG 的好处：

- 能使用私有知识。
- 能更新知识，不必重新训练模型。
- 可以提供来源。
- 比纯 prompt 更可靠。

## 风险

风险也不少：

- 检索错了，回答也会错。
- 文档过期会污染答案。
- 权限控制容易被忽略。
- 用户可能问到不该看的内容。
- 模型可能把不同文档混在一起。

传统软件工程关注数据库权限，RAG 还要关注知识库权限和上下文泄漏。

key：

- RAG = 检索 + 上下文 + 生成。
- RAG 工程质量取决于数据、检索、prompt 和评估。
- RAG 不是消除幻觉，只是降低幻觉并提供依据。
