## 故障类型

```
事务故障：单个事务内部错误（除零、违反约束）→ 回滚该事务
系统故障：操作系统崩溃、断电 → 重启后恢复内存中未写入的数据
介质故障：磁盘损坏 → 需要备份+日志重做
```

## 日志（Log）

记录事务对数据库的每次修改：

```
<T1, start>
<T1, A, 100, 90>    -- 事务T1将A从100改为90
<T1, commit>
```

**先写日志原则（WAL）**：必须先将日志写入磁盘，再修改数据库。

## 恢复策略

### 事务故障恢复

对该事务执行 **UNDO**（撤销）：反向扫描日志，将修改恢复为旧值。

### 系统故障恢复

重启后：
1. **REDO**（重做）：已提交但未写磁盘的事务，正向扫描日志重新执行
2. **UNDO**（撤销）：未提交的事务，反向扫描日志撤销修改

### 检查点（Checkpoint）

定期将内存中的修改写入磁盘并记录检查点，恢复时只需从**最近检查点**开始，不用扫描全部日志。

```
检查点之前已提交的事务 → 不需要REDO
检查点之后的事务 → 根据是否commit决定REDO还是UNDO
```

## 常见坑

- UNDO 是**反向**扫描日志，REDO 是**正向**扫描日志
- 介质故障必须有**数据备份**，光靠日志无法恢复（数据文件本身坏了）
- WAL 是所有数据库系统的基础，MySQL、PostgreSQL 都遵循这个原则
