## 软件架构的定义

软件架构 = **组件** + **连接件** + **约束（拓扑结构）**

- **组件**：系统中有意义的计算单元（服务、模块、进程）
- **连接件**：组件之间的交互机制（调用、事件、管道、消息）
- **约束**：组件和连接件的拓扑关系和规则

## 经典架构风格

### 数据流风格

**管道-过滤器（Pipe and Filter）**：
- 数据从一个过滤器流向下一个过滤器，通过管道传递
- 过滤器之间无共享状态，彼此独立
- 优点：可重用、可组合、支持并发
- 缺点：不适合交互式系统，共享数据困难
- 典型场景：Unix 命令行（`cat file | grep xxx | sort | uniq`）、编译器流水线

**批处理序列**：
- 与管道-过滤器类似，但数据是整批处理，不是流式

### 调用/返回风格

**分层架构（Layered）**：
- 系统分为若干层，每层只能调用相邻下层的服务
- 优点：关注点分离，高层不依赖低层实现
- 缺点：层间调用有性能开销，并非所有系统都适合严格分层
- 典型：OSI七层网络模型、Web三层架构（表现层-业务层-数据层）

**主程序-子程序**：传统的过程调用，子程序是被动等待调用的组件

**面向对象（OO）**：组件是对象，通过方法调用交互，支持封装、继承、多态

### 独立构件风格

**事件驱动（隐式调用）**：
- 组件不直接调用另一个组件，而是发布/订阅事件
- 发布者不知道谁会处理事件，松耦合
- 优点：解耦，易于扩展
- 缺点：难以控制执行顺序，调试困难
- 典型：GUI框架、消息队列（Kafka/RabbitMQ）

**微内核（Plug-in）**：
- 核心系统只提供最基本功能，其他功能通过插件扩展
- 优点：易扩展，插件可独立开发部署
- 缺点：插件间通信困难，内核设计困难
- 典型：Eclipse IDE、Chrome扩展、操作系统内核+驱动

### 虚拟机风格

- **解释器**：虚拟机解释执行程序（JVM、Python解释器）
- **规则系统**：推理引擎+规则库（专家系统）

### 仓库风格

**黑板架构**：
- 共享的数据空间（黑板）+ 多个知识源 + 控制器
- 知识源监视黑板，发现可处理的数据就进行处理并写回黑板
- 适合：解决方案不确定、多种算法协作、语音识别/模式识别
- 优点：各组件松耦合，可动态添加知识源
- 缺点：控制逻辑复杂，黑板是全局共享状态（并发问题）

**数据库系统**：以数据库为中心的仓库，是最常见的仓库风格

## MVC / MVP / MVVM

**MVC（Model-View-Controller）**：
```
用户操作 → Controller
Controller 更新 → Model
Model 通知 → View（直接观察或通过Controller）
```
- Model：数据和业务逻辑
- View：界面展示
- Controller：处理用户输入，协调M和V
- 缺点：View 和 Model 可能直接依赖，Controller 容易变臃肿

**MVP（Model-View-Presenter）**：
- View 和 Model 完全解耦，Presenter 承担所有逻辑
- View 只负责展示，被动接受 Presenter 的指令
- 优点：View 可以做单元测试（Mock Presenter）
- 适用：Android 早期开发模式

**MVVM（Model-View-ViewModel）**：
- ViewModel 暴露数据绑定，View 通过数据绑定自动更新
- 优点：View 和逻辑完全分离，适合响应式UI
- 典型：Vue.js、Angular、WPF

## C/S 与 B/S

| 对比 | C/S（客户端/服务器） | B/S（浏览器/服务器） |
|------|-------------------|-------------------|
| 客户端 | 需要安装 | 只需浏览器 |
| 更新 | 需要重新安装客户端 | 服务端更新，客户端自动更新 |
| 性能 | 高（本地计算） | 受网络影响 |
| 安全 | 较高（可以不暴露在外网） | 需要额外安全措施 |
| 适用 | 专业软件（CAD、游戏） | 通用应用（Web系统） |

## 架构风格的选择

| 场景 | 推荐架构风格 |
|------|------------|
| 数据处理流水线 | 管道-过滤器 |
| 企业应用分层 | 分层架构 |
| 高扩展性系统 | 微内核（插件） |
| 事件驱动系统 | 事件驱动 |
| AI/模式识别 | 黑板架构 |
| Web 应用 | B/S + MVC/MVVM |
